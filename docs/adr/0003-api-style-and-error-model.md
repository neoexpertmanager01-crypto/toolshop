# ADR 0003: Стиль API та модель помилок

- **Статус:** прийнято
- **Дата:** 2026-11-17

## Контекст

Клієнт (сторінка магазину) і майбутні інтеграції мають однаково розуміти відповіді API й помилки.
Потрібен один формальний опис API, з яким звіряється реалізація.

## Рішення

### Стиль REST

- Ресурси — іменники в множині: `/products`, `/products/{id}`.
- Методи: `GET` — читання, `POST` — створення, `PATCH` — часткове оновлення, `DELETE` — видалення.
- Тіла запитів і відповідей — JSON, поля в `camelCase`, дати — ISO 8601 (UTC).
- Запити й відповіді описуються окремими DTO (`ProductCreateRequest`, `ProductUpdateRequest`, `ProductResponse`),
  а не внутрішньою доменною моделлю.

### Єдиний формат помилки (`ErrorResponse`)

```json
{
  "error": "ValidationError",
  "code": "NAME_REQUIRED",
  "details": [{ "field": "name", "message": "Name is required" }]
}
```

- `error` — тип помилки (`ValidationError`, `NotFound`, `InternalError`);
- `code` — машинний код причини (`NAME_REQUIRED`, `PRICE_INVALID`, `PRODUCT_NOT_FOUND`, `INVALID_JSON`…);
- `details` — список помилок по полях (для валідації).

### Політика кодів статусу

| Код | Коли |
|-----|------|
| 200 | успішне читання чи оновлення |
| 201 | ресурс створено (`POST`) |
| 204 | ресурс видалено, тіла немає |
| 400 | некоректний JSON, невідоме поле, порушення правил валідації |
| 404 | ресурс або маршрут не знайдено |
| 500 | неочікувана помилка сервера (деталі лише в логах, не в відповіді) |

### Відповідність OpenAPI

`docs/api/openapi.yaml` — джерело правди про API. Будь-яка зміна ендпоінтів чи DTO спершу вноситься в
специфікацію, перевіряється в Swagger Editor, і лише потім реалізується в коді.

## Наслідки

- (+) Клієнт обробляє помилки однаково для всіх ендпоінтів і може показувати повідомлення біля конкретного поля.
- (+) Специфікацію можна використати для генерації клієнта чи тестів.
- (−) Специфікацію треба оновлювати разом із кодом.
