# ADR 0001: Стиль архітектури — модульний моноліт

- **Статус:** прийнято
- **Дата:** 2026-11-17

## Контекст

- Проєкт ToolShop — невеликий інтернет-магазин; зараз реалізовано каталог, далі будуть замовлення, оплата, доставка.
- Команда — 2 студенти, один репозиторій, спільний процес fork → pull request.
- Немає окремої інфраструктури: усе запускається локально (Node.js + PostgreSQL у Docker).
- Домен уже розбито на bounded contexts (практична 3): Користувачі, Каталог, Замовлення, Оплата, Доставка.

## Рішення

Продовжуємо як **модульний моноліт**: один Node.js-застосунок і одна база PostgreSQL.
Код ділиться на шари (`api/`, `service/`, `domain/`, `infrastructure/`, див. ADR 0002), а всередині `domain/` —
на модулі за bounded contexts (`catalog/`, `ordering/`, `payment/`…).

## Альтернативи

- **Мікросервіси** (окремий сервіс на кожен контекст): незалежне розгортання й масштабування, але для команди
  з 2 людей це зайва складність — мережеві виклики, розподілені транзакції, кілька баз, окремий CI для кожного
  сервісу. Переваги проявляються лише за великого навантаження чи кількох команд.

## Наслідки

- (+) Простий запуск, налагодження й тестування: один процес, одна БД, транзакції працюють «з коробки».
- (+) Один реліз — один артефакт (Docker-образ), простий CI/CD.
- (−) Масштабується лише цілим застосунком.
- (−) Межі модулів тримаються дисципліною: модулі не звертаються до таблиць інших контекстів напряму.

## Умови перегляду

Повертаємося до питання мікросервісів, якщо: окремий контекст (напр. Оплата) потребує незалежного масштабування
чи релізів; над проєктом працює кілька команд; або моноліт стає повільним у збиранні й розгортанні.
