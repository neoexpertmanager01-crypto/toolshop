# ADR 0002: Шарова архітектура

- **Статус:** прийнято
- **Дата:** 2026-11-17

## Контекст

Після практичної 1 весь код (маршрути, SQL, обробка помилок) був у `server.js`. Для CRUD і подальших модулів
потрібна структура, у якій бізнес-логіку можна тестувати без HTTP і без бази.

## Рішення

| Шар | Папка | Що зберігається |
|-----|-------|-----------------|
| API | `api/` | Express-роути: приймають HTTP-запит, передають тіло (DTO) у service/, повертають статус і JSON за контрактом `openapi.yaml`; `errorHandler` перетворює помилки в `ErrorResponse`. |
| Service | `service/` | Use-cases: валідація DTO, виконання операцій, мапінг DTO ↔ domain, помилки `ValidationError` / `NotFoundError`. |
| Domain | `domain/` | Сутності та їх інваріанти (`Product`, `Order`…), без залежностей від Express чи БД. |
| Infrastructure | `infrastructure/` | Доступ до PostgreSQL: пул з'єднань і репозиторії з SQL. |

Збирання залежностей — у `server.js` (pool → repository → service → app), складання Express-застосунку — в `app.js`.

**Напрямок залежностей — зверху вниз:** `api → service → domain`. Service отримує репозиторій як параметр
(`createProductService(repository)`), тому не залежить від конкретної БД.

## Заборонені зв'язки

- `api/` не звертається до БД і не містить бізнес-логіки й валідації — лише виклик service/.
- `domain/` не імпортує нічого з `api/`, `service/`, `infrastructure/`, Express чи `pg`.
- `service/` не знає про HTTP (`req`, `res`, статус-коди задаються лише через класи помилок).
- SQL пишеться тільки в `infrastructure/`.

## Наслідки

- (+) Юніт-тести service/ працюють з репозиторієм у пам'яті, без Postgres (`test/productService.test.js`).
- (+) Заміна БД чи фреймворку зачіпає один шар.
- (−) Більше файлів і «прокидання» даних між шарами навіть для простих операцій.
